# 移动应用整改核验台

描述应用版本、个人信息规则、整改事项和监管复核的关联方式。

## 领域资料

`contracts/` 约定基础资料格式,`fixtures/` 提供不含真实个人信息的示例。代码模块只负责读取和校验这些资料,后续业务服务可以沿用其中的领域标识与版本约定。

当前资料记录了以下业务事实:

- 通报列出四类个人信息收集使用问题
- 运营者需在十五个工作日内完成整改
- 后续将结合整改情况开展核查处置

## 输入资料

- `fixtures/problem-catalog.json`:四类问题分类(规则未公开、非必要权限频繁索取、告知不完整、账号无法注销)
- `fixtures/role-contract.json`:产品、法务、研发三方角色及其结论覆盖的证据类别
- `fixtures/notice.json`:监管通报,三十款应用(含小程序)的问题各自落到具体发布版本
- `fixtures/registry.json`:版本台账,记录各版本开始在线的时间;同一应用允许灰度版、全量版、旧版等多个版本同时在线
- `fixtures/holidays.json`:示例节假日,用于工作日计算

## 领域模块

- `src/workdays.py`:工作日期限计算
- `src/catalog.py` / `src/notice.py`:输入资料的读取与校验
- `src/registry.py`:版本台账,下架只追加记录,不改写历史在线区间
- `src/evidence.py`:五类证据(数据用途、权限触发、告知文本、第三方组件、注销路径),按生效时间定位
- `src/events.py`:事件流,灰度发布、旧版下架、用户撤回授权、复测失败、逾期等只增不改
- `src/signoff.py`:三方按轮次分别签署结论,同一角色同一轮次不得覆盖
- `src/service.py`:核验服务门面,登记通报、留存证据、签署结论、记录生命周期事件
- `src/audit.py`:监管回查,还原某时刻用户实际看到的规则与操作结果

## 期限约定

- 期限自通报日期的次日起数,周末与节假日不计入工作日
- 期限日当天仍属期限内,次日起才算逾期
- 示例:通报 2026-09-07,十五个工作日,示例节假日 2026-09-25 不计入,期限为 2026-09-29

## 只增不改原则

所有台账、证据、事件与签署记录只追加不覆盖:灰度发布、旧版下架、用户撤回授权、复测失败和逾期都以新记录表达,先前记录保持原样。复测失败开启新一轮签署,先前轮次的结论完整保留。

## 监管回查

`RemediationService.audit_at(app_id, when)` 返回该时刻的快照:在线版本(含灰度)、各版本当时生效的告知文本、当时已发生的操作结果与撤回授权记录。后来的整改、发布与下架不会改写较早时刻的回查结果。

## 本地校验

运行项目自带测试可确认示例资料能够读取,且领域标识、版本和事实列表完整。示例中的编号均为虚构值,不包含账号、凭据或真实主体信息。

```sh
python3 -m unittest discover -s tests
```
