# 移动应用整改核验台

描述应用版本、个人信息规则、整改事项和监管复核的关联方式，并提供一套只追加不覆盖的整改核验服务。

## 领域资料

`contracts/context.schema.json` 约定基础资料格式，`fixtures/context.json` 提供不含真实个人信息的示例。代码模块只负责读取和校验这些资料，后续业务服务可以沿用其中的领域标识与版本约定。

当前资料记录了以下业务事实：

- 通报列出四类个人信息收集使用问题
- 运营者需在十五个工作日内完成整改
- 后续将结合整改情况开展核查处置
- 监管问题落实到具体发布版本，应用与小程序可能多版本同时在线
- 数据用途、权限触发、告知文本、第三方组件、注销路径五类证据按版本留存
- 产品、法务、研发分别签署结论，灰度发布、旧版下架、用户撤回授权、复测失败与逾期只追加记录不覆盖
- 监管回查按时间点定位用户当时实际看到的规则与操作结果

## 输入契约

核验服务的两类输入以契约形式固化，示例见 `fixtures/`：

- `contracts/problem_catalog.schema.json`：问题分类目录。声明五类证据（数据用途、权限触发、告知文本、第三方组件、注销路径），并为规则未公开、非必要权限频繁索取、告知不完整、账号无法注销四类问题分别约定闭环所需的证据种类。
- `contracts/roles.schema.json`：角色契约。产品、法务、研发各自签署本人职责范围内的结论，三方全部通过且证据齐全才算闭环。

## 核验服务

`src/service.py` 的 `VerificationService` 以追加式台账实现核验：

- **问题落到版本**：`file_problem` 把监管问题登记到具体应用的具体发布版本，多版本同时在线互不影响；整改期限自登记次日起按工作日计算（`src/workdays.py`，默认十五个工作日，可传入节假日）。
- **证据留存**：`attach_evidence` 按五类证据种类留存，同类新证据不覆盖旧证据。
- **三方签署**：`sign_conclusion` 记录每个角色本人的结论；复测失败（`record_retest_failure`）后需重新签署，但历史签署全部保留。
- **只追加事件**：灰度发布、旧版下架、用户撤回授权、复测失败、逾期（`mark_overdue`，幂等）都以新事件记录，任何先前记录都可按 `timeline` 回溯。
- **监管回查**：`user_view(app_id, at=...)` 重建某一时刻用户实际看到的在线版本（含灰度比例）、当时有效的各类证据文本、未闭环问题与已撤回授权的用户引用；版本下线或证据更新不影响按更早时间点重建。

所有事件时间须携带时区；示例中的编号均为虚构值，不包含账号、凭据或真实主体信息。

## 本地校验

运行项目自带测试可确认示例资料能够读取，且领域标识、版本和事实列表完整：

```sh
python3 -m unittest discover
```
